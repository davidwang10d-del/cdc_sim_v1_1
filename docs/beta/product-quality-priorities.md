# CDC Sim private-beta product quality priorities

## Purpose and evidence

This report turns the current prototype into a commercial-readiness backlog. It focuses on changes that affect a paying organization's ability to install, operate, recover, update, and obtain support. It intentionally excludes minor style cleanup and refactoring that has no visible business result.

The assessment is based on the current Windows launch scripts, Flask routes, readiness page, tactical dashboard, scenario editor, persistence code, scenario-package checks, and automated tests.

Current strengths worth preserving are the data-only scenario boundary, validation before a scenario replaces the running session, atomic checkpoint writes, validated backup restore, per-version user-data separation, default loopback binding, local core browser assets, privacy-safe diagnostics, visible GIS fallback status, and broad engine regression coverage. The remaining release risks are clean-machine installer proof, application lifecycle polish, exact save/package identity, upgrade safety, and an operational support process.

## Priority and difficulty scale

- **P0** blocks a dependable external beta or creates a high risk of data loss or failed launch.
- **P1** should follow during the beta because it materially affects adoption, support cost, or paid-content reliability.
- **P2** belongs after the local private beta and before broader organization or hosted deployment.
- **Small** is usually up to two focused engineering days. **Medium** is several days and crosses components. **Large** is a multi-sprint product capability or requires outside operational work.

## Recommended release sequence

1. Finish and sign the installer artifact, then verify the integrated runtime, version display, backups, safe errors, and local browser dependencies in the packaged build.
2. Build once from a clean checkout and stamp immutable build metadata.
3. Run the complete automated suite against that revision, then install the resulting artifact on clean Windows 10 and Windows 11 machines.
4. Complete a chair journey: launch, status check, mount a supplied scenario, issue an order, save, export a backup, restart, import, restore, and produce a SITREP.
5. Malware-scan the final installer, record its SHA-256 value, and deliver the exact artifact through the private beta channel.
6. Begin with a small cohort and log onboarding time, failed launches, session recovery success, and support issues. Promote P1 work using those results.

## Beta quality metrics

Use business-facing measures rather than code volume:

- At least 90% of invited testers complete first launch without support.
- Median Download → Play time is under five minutes on a supported PC and connection.
- Every shipped build is traceable by version, build ID, source revision, build time, and artifact hash.
- A checkpoint backup restores successfully on a second clean profile in every release acceptance run.
- No P0 defect remains open when a beta build is distributed.
- No customer data, absolute path, credential, or raw exception appears in public diagnostics.
- Support can classify every beta report from build ID, support ID, action, expected result, and actual result without first requesting the entire scenario pack.
